# M1 test results

Recorded 2026-10-08 and 2026-10-09 on the author's machine (Intel Core i7-13700H, 13.7 GB RAM,
Windows 11, Temurin JDK 21.0.12.1, Maven 3.9.11, JUnit 6.1.3), while other builds and a GPU job ran
in parallel. Every JVM ran with a capped heap and `-XX:-UsePerfData`: Maven with `-Xmx512m`
(`.mvn/jvm.config`), the surefire fork with `-Xmx512m`, the replay tool with `-Xmx1g`. CI re-runs
the same steps on Ubuntu with Temurin 21 on every push; CI results are not recorded here.

The work follows DMAIC: the problem and the critical-to-quality (CTQ) targets are defined in
[RFC 0001](../rfc/0001-design.md#critical-to-quality-measures-define); this file covers Measure,
Analyze, Improve and Control. The full hit-rate table is
[m1-hit-rates.tsv](m1-hit-rates.tsv) (125 cells plus one ceiling row per trace).

## Commands

`make` is not installed on this Windows machine, so the Makefile targets were run as the same
commands (`LAB` stands for `java -Xmx1g -XX:-UsePerfData -cp target/classes portfolio.cacheevictionlab.cli.Main`):

```bash
mvn -B -q -DskipTests dependency:resolve            # make setup
mvn -B -q -DskipTests compile                       # make lint: enforcer, Spotless check, -Xlint:all -Werror
mvn -B verify                                       # make test
$LAB fetch                                          # make fetch: 5 pinned traces, 217 MB, size + SHA-256
$LAB bench --out docs/results/m1-hit-rates.tsv      # make results: recorded the table
$LAB bench --expect docs/results/m1-hit-rates.tsv   # make bench: second run, must match every cell
$LAB bench --mode every-request --out .tmp/every-request.tsv   # ADR 0002 comparison (one run)
$LAB fetch --only cluster045 && $LAB bench --only cluster045 --expect docs/results/m1-hit-rates.tsv  # make e2e
mvn -B -q dependency:list -DincludeScope=test -DoutputFile=target/dependencies.txt
python scripts/osv_audit.py Maven target/dependencies.txt                                         # make audit
```

The full local check (setup, lint, test, e2e, audit) ran twice in a row; both passed with identical
results (the replay has no randomness and no timing input). After the numbers were recorded, the
downloaded traces were deleted (`data/` is git-ignored); `make bench` fetches them again from
`traces/pins.tsv` and deletes them when it finishes. The e2e step downloaded cluster045 fresh on
both check runs, which exercised the download path (HTTPS, no redirects, size and SHA-256 checked).

## Analyze

- **Correctness held before any comparison.** Every policy matched its brute-force model on all
  600,000 random operations and 80,000 read-and-fill requests; no cell of any replay beat the
  never-evicting ceiling (`above_infinite=0`), which `Main` checks on every run.
- **ARC or W-TinyLFU is best in all 25 cells; LRU is never best.** W-TinyLFU wins 14 cells
  (every size of cluster017 and cluster044, and 4 of 5 of cluster024), ARC wins 11 (every size of
  cluster045 and cluster052, and cluster024 at 0.1%). The best policy beats LRU by 0.91 points
  (cluster052, 5%) to 11.95 points (cluster017, 0.5%), mean 4.54 points.
- **The gap is largest when the cache is small.** On cluster017 at 0.1% of the keys, W-TinyLFU's
  23.46% is twice LRU's 11.55%; at 10% the two are 4.2 points apart.
- **LFU depends on the workload.** It beats LRU on cluster017 and cluster045 at every size but loses
  to it at every size on cluster024, cluster044 and cluster052, by up to 14.7 points (cluster052,
  1%). In-cache LFU never ages its counts, so keys that were used often earlier stay resident;
  ARC's adaptive target and W-TinyLFU's halving are designed to avoid that. M1 does not measure
  how popularity drifts within each trace, so this is the likely cause, not a proven one.
- **FIFO is below LRU in all 25 cells** on these traces, by 0.49 to 5.48 points.
- **cluster045 is dominated by compulsory misses:** 838,523 distinct keys in 1,000,000 requests,
  so even a cache that never evicts hits only 20.70% of reads. At 10% of its keys the best policy
  reaches 82.8% of that ceiling; on the other traces the best policy at 10% reaches 86.5 to 88.6%.
- **Replay mode matters for absolute numbers, not for the winner** (ADR 0002): in every-request
  mode the ceiling of cluster045 drops from 20.70% to 16.15% and single cells move by -3.75 to
  +4.24 points, but the best policy is the same in all 25 cells and the full order changes in 5.
- **Defects found while building, and their root causes:**
  - `wTinyLfuRejectsOneHitWondersThatWouldDisplaceFrequentKeys` first required all 150 frequent
    keys to survive a 2,000-key scan; 148 did. Debugging showed the two admitted newcomers had a
    sketch estimate of 6 against the victim's 5: all four of their counters collided with
    frequent keys. Root cause: a Count-Min sketch over-counts by design, so the assertion was too
    strict, not the policy wrong. The test now allows at most 5 of 150 and still requires LRU to
    keep none. Investigating it led to the sketch-width change below.
  - The first version of `PolicyBehaviourTest.arcMovesItsTargetTowardsTheGhostListThatWasHit`
    expected a B1 ghost after filling T1 with 4 keys and adding a fifth. In the paper's Case IV(A),
    when T1 alone holds `c` keys the oldest is dropped with no ghost; the test was rewritten to
    first put a key in T2. The reference model and the implementation agreed with the paper; the
    test's expectation was wrong.
  - The first trace choice included cluster015, which is 99.9% `set`; replaying it look-aside
    would have measured 1,201 reads. Root cause: choosing by file size without reading the op
    mix. Every trace's op counts are now printed by the replay and recorded above.

## Improve

| Change | Measured effect |
|---|---|
| W-TinyLFU sketch width 4 x capacity instead of 1 x capacity (ADR 0003) | hit rate up in all 25 cells, by 0.05 to 1.22 points, mean 0.51; for example cluster044 at 0.1%: 28.74% to 29.95%, cluster045 at 1%: 11.53% to 12.14% |
| One pass feeds all 25 caches of a trace (instead of one pass per cache) | each trace is read twice (survey, replay) instead of 26 times; `replayingAllCachesInOnePassEqualsReplayingEachAlone` proves the results are identical |
| Look-aside replay as the default (ADR 0002) | cluster045's 226,141 `add` requests are no longer counted as misses: its ceiling is 20.70% of reads instead of 16.15% of requests |

The width comparison used the same five traces and sizes; the 1 x capacity numbers came from the
first full replay, before the change (kept in the git-ignored `.tmp/improve/`).

## Control

- **Unit tests hold every correctness CTQ:** `ReferenceModelTest` (0 differences from the
  brute-force models), `CacheContractTest` (size never above capacity, `contains` has no side
  effects, evict removes exactly one key), `ReplayerTest` (no policy above the ceiling, one pass
  equals separate passes), `TracePinTest` and `TwitterTraceReaderTest` (pins and input bounded and
  validated). All randomness uses fixed seeds.
- **Runtime gates:** every `replay` and `bench` exits with 3 if any cell beats the ceiling or, with
  `--expect`, differs from the committed table; `bench` re-hashes every trace against its pin before
  replaying it.
- **CI gates** (`.github/workflows/ci.yml`): Spotless check and `-Xlint:all -Werror` fail the build;
  `make e2e` downloads cluster045 by its pin, replays it and requires the 26 committed rows of that
  trace exactly, printing the `RESULT` line as a `::notice` (or `::error`); the OSV audit fails on
  any known vulnerability.
- **Mistake-proofing in the code:** capacities, list options, percentages, pins (name pattern,
  HTTPS host allow-list, size limit, SHA-256 format) and results files are validated; downloads stop
  past the pinned size and are renamed into place only after the hash matches; lines over 4,096
  bytes are skipped and counted.
- **Reproducible build:** pinned plugin versions, Enforcer for JDK and Maven versions, a fixed
  `project.build.outputTimestamp`, Actions pinned to commit SHAs.
